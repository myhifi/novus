Legacy Audit & the Novus / Foundation

Verify every bug in the legacy MERN storefront against the real source code, then establish a clean Next.js 16 + Prisma 6 + Neon scaffold in a sibling e-shop/ folder. The legacy front/, admin/, back/ trees remain untouched as reference — the new app is a separate git repository.

1 Overview

Goal. Before writing a single line of new code, prove every claim in the bug inventory against the actual source files. Then stand up shop/ with the same production patterns proven in the earlier Lumière project — no regressions, no re-litigating decisions.

Deliverables

  1. A verified bug table — every inventory item, checked against the source, with file:line evidence.
  2. A second look for bugs the original audit missed.
  3. A scaffolded shop/: Next.js 16, TypeScript, Tailwind 4, Prisma 6, ESLint, Prettier, Husky.
  4. Working prisma validate and prisma generate against a Neon connection.
  5. A green npm run build with PrismaPlugin active.
  6. The Lumière deployment gotchas baked in from day one — prisma-client-js, binaryTargets, --webpack, direct Neon endpoint.

2 Audit Strategy

The legacy codebase is 40+ files across three Vite/CRA-style apps. Every bug listed in the brief was re-read against the actual source — no assumptions, no “probably still true.” Where the brief's summary was imprecise, I corrected it in the table.

Rule followed If the audit disagrees with the brief, the audit wins — and the difference is documented. Fixing a bug that was already fixed would be wasted work; missing one that's still live would be worse.

The inventory was split into four categories:

3 CRITICAL Bugs — Verified

#1 — all_products imported from a commented-out export

FileEvidence
front/src/assets/data.jsThe export block is entirely commented out starting at the banner // export const all_products = [...]. Only categories is live.
front/src/components/Categories.jsximport { categories, all_products } from "../assets/data" — the second name is undefined at runtime.
front/src/components/Offer.jsxSame import. Then all_products.slice(0, 12) — a TypeError on load.

Verdict: confirmed live. Both routes crash with Cannot read properties of undefined (reading 'slice').

Root cause Two sources of truth — the API in ShopContext and the static data.js — were patched at different times. Deleting the static source without updating its consumers broke them silently.

#2 — Admin order list always empty

SideCode
Frontend readsadmin/src/components/Orders.jsx → setOrders(res.data.orders.reverse())
Backend returnsback/controllers/orderController.js → res.json({ success: true, data: orders })

Verdict: confirmed. res.data.orders is undefined → .reverse() throws inside the try/catch, the catch logs and swallows, and the UI is left empty with a red toast.

#3 — Three placeholder components shipping dead code

FileBody

front/src/components/ProductDisplay.jsxreturn <div>ProductDisplay</div>

Verdict: confirmed. All three are memo()-wrapped single-line stubs. Nothing imports them — they exist as dead code. Decision recorded in Phase 4: delete, don't implement. Their intended responsibilities are already covered by Header.jsx, Categories.jsx, and Product.jsx.

4 SECURITY Bugs — Verified

#4 — Admin login bypasses the backend entirely

// admin/src/components/AdminLogin.jsx
if (formData.email === "admin@gmail.com" &&
    formData.password === "123456") {
  localStorage.setItem("admin", "true");
  navigate("/admin/add");
}

Verdict: confirmed. Any visitor reading the bundled JS sees the credentials. The backend adminLogin controller exists but is never called.

#5 — ProtectedRoute checks a key nothing writes

// admin/src/components/ProtectedRoute.jsx
const token = localStorage.getItem("adminToken");
if (!token) return <Navigate to="/admin/login" replace />;

Verdict: confirmed. A repo-wide grep for setItem("adminToken" returns nothing in admin/src/. Login stores "admin", not "adminToken". The proper flow is unreachable.

#6 — Public setupFirstAdmin endpoint

// back/routes/adminRoutes.js
adminRouter.post("/setup", setupFirstAdmin);  // no middleware

// back/controllers/adminController.js
const existingAdmin = await userModel.findOne({ isAdmin: true });
if (existingAdmin) return res.json({ success: false, ... });
// ...else create a new admin with attacker-supplied credentials

Verdict: confirmed. On a fresh database, the first caller to hit POST /api/admin/setup becomes the admin. The endpoint never gets deleted because the developer forgets.

#7 — Committed .env files, including Stripe keys

FileCommitted secret
back/.envMONGO_URL, JWT_SECRET, STRIPE_SECRET_KEY
front/.envVITE_STRIPE_PK (publishable — lower risk, but still)
admin/.envVITE_API_URL (harmless)

Both .gitignore files contain *.local but not .env. Confirmed by direct inspection of the .gitignore contents.

Phase 10 action item Rotate the legacy JWT_SECRET and STRIPE_SECRET_KEY even though shop/ is a fresh repo — the old keys remain in the legacy git history and are public if that repository is ever pushed.

#14 — Multer accepts anything, no filename sanitization

// back/routes/productRoutes.js
const storage = multer.diskStorage({
  destination: "uploads",
  filename: (req, file, cb) =>
    cb(null, `${Date.now()}-${file.originalname}`),
});
const upload = multer({ storage });  // no fileFilter, no limits

Verdict: confirmed. No fileFilter (accepts .exe, .html, .svg — stored as-is, served back from /images/*). No limits (unbounded size). The filename is trusted verbatim — a crafted originalname like ..%2F..%2Fetc%2Fpasswd can escape the uploads/ directory depending on OS behavior.

5 LOGIC Bugs — Verified

#8 — Two sources of truth for products

ShopContext.jsx fetches from /api/product/list on mount. But Categories.jsx and Offer.jsx import all_products directly from data.js. The two systems were never reconciled — that's how #1 slipped through.

Verdict: confirmed.

#9 — getTotalCartAmount briefly returns $0

// front/src/context/ShopContext.jsx
const getTotalCartAmount = () => {
  return Object.entries(cartItems).reduce((total, [id, qty]) => {
    const product = all_products.find((p) => p._id === id)
    return total + (product ? product.price * qty : 0)
  }, 0)
}

On page load, all_products is [] until the fetch resolves. During that window, every lookup returns undefined, the guard collapses to 0, and the total is silently $0 even for a full cart.

Verdict: confirmed. The guard prevents NaN, but the transient $0 is a real UX bug.

#10 — Orphaned cart keys after product deletion

The current getTotalCartAmount does guard with product ? ... : 0, so NaN doesn't occur — the brief's description is slightly stronger than reality. But the orphaned key still lives in cartItems forever, and the legacy Cart.jsx silently filters it out. That means a user can see a cart line disappear without explanation.

Verdict: partially confirmed — no NaN, but still orphaned-key state.

#11 — removeFromCart ignores backend failure

const removeFromCart = async (id, removeAll = false) => {
  setCartItems((prev) => { /* optimistic update */ });
  if (token) {
    try {
      await axios.post(`${API_URL}/api/cart/remove`, { id }, { headers: { token } });
    } catch (err) {
      console.log("Cart remove error:", err);   // ← swallowed
    }
  }
}

Verdict: confirmed. Optimistic removal stays in the UI; the server keeps the item. Next page reload re-syncs from the backend and the item reappears — the user's click appears to have done nothing.

#12 — No JWT expiry handling

// back/middleware/auth.js
try {
  const token_decode = jwt.verify(token, process.env.JWT_SECRET);
  req.userId = token_decode.id;
  next();
} catch (err) {
  res.json({ success: false, message: err.message });  // raw JWT error
}

The token lives 7 days. After expiry, jwt.verify throws TokenExpiredError, the middleware returns it verbatim, and no client code distinguishes expiry from “not logged in.” The user is stuck with a stale token in localStorage forever.

Verdict: confirmed.

#13 — No stock check at order time

placeOrder reads req.body.items, builds a Stripe session, and persists the order — but back/models/productModel.js has no stock field at all. There is nothing to check.

Verdict: confirmed. Stock tracking has to be introduced as a new capability, not fixed as a bug.

#15 — No duplicate slug/name check on products

addProduct inserts unconditionally. There is no unique index on name in the schema and no pre-insert query.

Verdict: confirmed.

#16 — Stripe flow has no webhook

const session = await stripe.checkout.sessions.create({
  line_items,
  mode: "payment",
  success_url: `${frontend_url}/verify?success=true&orderId=${newOrder._id}`,
  cancel_url:  `${frontend_url}/verify?success=false&orderId=${newOrder._id}`,
});

Order state is driven by the browser hitting /verify. If the user closes the tab after paying, payment: true is never set. If the user manually visits /verify?success=true&orderId=xyz, an unpaid order is marked paid.

Verdict: confirmed. Correct fix is a signature-verified webhook at /api/webhooks/stripe (Phase 6).

6 Additional Findings — Beyond the Inventory

Two extra issues surfaced during the audit pass. Neither was in the original brief.

A — userController.registerUser trusts bcrypt in the wrong order

const salt = await bcrypt.genSalt(10);
const hashedpassword = await bcrypt.hash(password, salt);

This works, but it's duplicated in adminController.setupFirstAdmin with the same code. When the app moves to Next.js, this pattern collapses into one hashPassword() helper — otherwise password policies drift between the two call sites. Recorded for Phase 3.

B — adminController.adminLogin leaks whether an email exists

CaseResponse
Email not found{ success: false, message: "User Not Found" }
Email exists, not admin{ success: false, message: "User Not an Admin" }
Email exists, admin, wrong password{ success: false, message: "Invalid Password" }

Three distinct messages → an attacker can enumerate valid emails and privileged accounts by reading the response text. The Phase 3 fix is the standard pattern: one generic error for all failure modes.

Not in the original inventory Fixing this in the new build is not “scope creep” — it's a free improvement because the login flow is being rewritten anyway.

7 Architectural Decisions

7.1 — A new sibling folder, not a rename

shop/ sits next to front/, back/, and admin/. Nothing in the legacy trees is modified. The reference implementation stays runnable until the new app fully replaces it.

AlternativeRejected because
Rename front/ → shop/Destroys the reference; forces a hard cutover mid-project
Monorepo with workspacesAdds complexity with zero payoff for a single-app rewrite
Subfolder of the legacy repoMixes histories; git blame becomes unusable

7.2 — Fresh git repository

shop/ gets its own .git. The legacy repo's history includes committed .env files (#7) — separating the histories means those secrets never appear in the new repo's blame, logs, or commit graph.

7.3 — Neon from day one (no SQLite stopover)

The earlier Lumière build started on SQLite and migrated later. That migration produced five distinct deployment errors — the pattern is well understood now, and there is nothing to gain from repeating it. Using Neon from Phase 1 means Phase 1's schema.prisma is identical to Phase 10's, minus the models.

7.4 — Webpack, not Turbopack

PrismaPlugin is a webpack plugin. Any project that uses it must build with Webpack. Rather than fight this later, the --webpack flag is added to both dev and build in Phase 1's package.json — this is the same decision made after five errors on Lumière, now applied preemptively.

9 Scaffolding Steps

Full step list lives in the phase's companion document. The high-level order:

  1. npx create-next-app@latest shop from the parent directory — TypeScript, Tailwind, src/, App Router, no Turbopack.
  2. Pin Prisma to 6.x if the scaffolder pulled an RC (the Lumière gotcha).
  3. Install supporting tooling: Prettier, Husky, lint-staged, tsx, dotenv, @prisma/nextjs-monorepo-workaround-plugin.
  4. npx prisma init --datasource-provider postgresql, then replace the generated schema with the Phase-1 skeleton.
  5. Write prisma.config.ts with a CI-safe fallback URL.
  6. Add src/lib/prisma.ts — hot-reload-safe singleton.
  7. Wire PrismaPlugin into next.config.ts.
  8. Add scripts/generate-local-images.ts and its predev/prebuild hooks.
  9. Add --webpack to dev and build.
  10. Husky + lint-staged wired to a pre-commit hook.
  11. Extend .gitignore; create .env and .env.example.
  12. Green build, silent typecheck, initial commit.

14 Summary

Audit — all 16 inventory items verified

  • CRITICAL (3). Broken imports crash two public routes; admin order list is always empty; three files are dead placeholders.
  • SECURITY (4). Login bypass with hardcoded credentials; a protected-route key that nothing writes; a public admin-claim endpoint; committed .env files; unrestricted Multer uploads.
  • LOGIC (9). Two sources of truth; transient $0 cart total; orphaned cart keys; ignored backend failure on cart mutations; no JWT expiry handling; no stock tracking; no duplicate-slug check; no Stripe webhook.
  • Additional findings (2). Duplicated bcrypt code paths, and a user-enumeration leak in adminLogin (three distinct error messages).

Scaffold — everything needed for Phase 2

  • Next.js 16 + TypeScript 5 + Tailwind 4, App Router, src/, no Turbopack.
  • Prisma 6 pinned; schema with the RHEL binary target; prisma.config.ts with a CI-safe fallback.

  • Prettier + ESLint + Husky + lint-staged — pre-commit hook active.
